# Experimental 300-baud FX.25 — testers only

**No hardware, on-air, HF-channel or PTT acceptance is claimed.** This draft
extends the separately proposed 1200-baud implementation (upstream #687).
Automated results are recorded below separately from physical acceptance.
Do not treat a passing simulation or a local TX log as evidence of RF delivery.

## Configuration and compatibility

Native modem-backed AFSK, **300 baud, 1600 Hz mark / 1800 Hz space** only.
An input audio-device binding remains required. FX.25 RX runs automatically,
alongside ordinary AX.25, even when `fx25_encode` is false. No RX opt-in is needed.
TX defaults **off**. Select FX.25 transmit deliberately; before saving a new
300-baud TX opt-in or changing its parity/output configuration, the editor asks
for explicit confirmation of the experimental status and airtime cost. Cancel
leaves the channel unsaved. API users opt in explicitly with `fx25_encode: true`;
the confirmation is a UI acknowledgement, not a new API security permission.

`fx25_mode` retains `auto`, `16`, `32` and `64`. Oversized packets fall back to
ordinary AX.25 with explicit metadata, without truncation. No protocol, database
or IPC fields are added. A one-time data migration clears any inert 300-baud
FX.25 TX flag saved by older versions, so upgrading cannot silently enable
experimental transmission. Explicit opt-ins made afterward survive restarts. Existing 1200-baud channels and defaults are preserved.
Other rates, tone pairs, PSK/G3RUH and KISS-only FX.25 TX remain unsupported.
External KISS TNCs control their own modulation and FEC.

Receive decoding itself adds **no transmit airtime**. Existing digipeating,
gating, beacon and TX-governor rules still apply: a newly decoded packet can
trigger configured forwarding, including ordinary AX.25 forwarding while FX.25
TX is off. Enabling FX.25 TX applies to channel transmissions from all existing
sources; it is not restricted to a manual test or a beacon.

## Airtime: what the numbers mean

The standard adds an 8-byte correlation tag, Reed-Solomon parity, and padding
to one of its defined data-block sizes. At 300 bit/s:

| Parity bytes | Tag + parity bits | Time for tag + parity alone |
|---:|---:|---:|
| 16 | 192 | 0.640 s |
| 32 | 320 | 1.067 s |
| 64 | 576 | 1.920 s |

These are **not total frame durations or an exact additional-time estimate**.
Padding, byte alignment and embedded HDLC flags add further overhead. The
ordinary packet also has FCS, bit stuffing and key-up/tail flags. Standard tag
selection changes discretely with protected frame size; there is no universal
percentage increase. Auto chooses the existing standard policy, not the mode
proven best for a particular HF link. Fixed 64 is not an automatic recommendation.

For generated FX.25 audio, time is `(outer flags + 8 + data capacity + parity)
* 8 / 300`, with the configured outer flag counts rounded up. Compare this with
the ordinary encoder's actual bit count for the **same frame, delay and tail**.
Use the offline `fx25_audio airtime HEX PARITY` command with
`GRAYWOLF_FX25_BAUD=300` for sample-count measurements. The largest supported
standard codeword plus tag occupies 7.013 s, before outer delay/tail flags.
Per-packet keying overhead and real radio behavior must be measured separately.

Measured sample-count examples (seconds), using the generic APRS/N0CALL-7
header and `x` payload from `scripts/fx25/stress300.py`, raw AX.25 length before
FCS, 48 kHz PCM, 300 ms delay and 100 ms tail (rounded to whole flags):

| Frame bytes | Ordinary AX.25 | Auto | Fixed 16 | Fixed 32 | Fixed 64 |
|---:|---:|---:|---:|---:|---:|
| 20 | 1.027 | 1.920 | 1.920 | 2.347 | 4.053 |
| 60 | 2.087 | 4.907 | 4.480 | 4.907 | 5.760 |
| 100 | 3.153 | 4.907 | 4.480 | 4.907 | 5.760 |
| 180 | 5.287 | 7.440 | 7.440 | 7.440 | 7.440 |
| 236 | 6.780 | 6.780* | 6.780* | 6.780* | 6.780* |

`*` Explicit ordinary AX.25 oversized fallback, not FEC transmission. The
60-byte Auto example occupies about 135% more time (2.35 times as long); the
100-byte Auto example about 56% more. They are specific generated packets,
not estimates for every APRS packet, and not instrumented radio keying results.


### Benefit and shared-channel tradeoff

The RS modes can correct up to 8, 16 or 32 erroneous byte symbols in a protected
block, respectively, provided correlation, framing and embedded FCS validation
succeed. This can recover some damaged packets that ordinary HDLC/FCS discards.
It does not recover arbitrary collisions, long fades, missing tags or unlimited
errors. An uncorrectable block must not be reported as repaired. A legacy
receiver may decode a clean embedded ordinary AX.25 frame but cannot use its
FEC parity to repair errors.

On a clean link the extra bits consume capacity without a correction benefit.
Longer transmissions occupy a shared channel longer and can increase collision
exposure. They are often a poor tradeoff on a busy channel without demonstrated
delivery improvement. FEC does not solve congestion or replace normal channel
access. If it prevents retries in an acknowledged application, useful throughput
may improve under some error conditions; APRS broadcasts are not thereby given
acknowledgements or an automatic retry mechanism.

Plausible **test scenarios**, not established HF performance claims, include
coordinated low-traffic links with intermittent correctable errors, asymmetric
links where only the weaker sender benefits, and controlled experiments with
FEC-capable receivers comparing delivery per occupied second. Start with quiet,
coordinated channels and ordinary AX.25 as the baseline. Neither an RF sensitivity
gain nor superiority over Dire Wolf has been measured for this 300-baud branch.

Stress waveforms use pinned Dire Wolf `gen_packets`. AWGN is deterministic,
referenced to whole-record RMS; the clock experiment changes both tone and baud
by changing WAV sample rate. These few synthetic cases are not sensitivity
thresholds, RF bandwidth/offset tolerance guarantees, long-term stability tests,
or a substitute for independent on-air acceptance. Exact observed waveform
hashes and airtime results are in [the machine-readable record](fx25-300-results.json).

The +/-1% cases initially exposed duplicate deliveries from nominal-rate event
backdating. The 300-baud path now maps the embedded closing flag to actual sampled
bit times, bounded to 2040 timestamps per active slicer. Duplicate history also
covers the bounded FEC latency (up to 8.5 seconds at 300 baud); matching remains
within three symbol times, preserving distinct repeated transmissions. These
stress regressions and long-delayed-event unit tests now pass.

The broad Rust library run has 226 passes and five previously documented
unchanged environment failures: missing sound output, three prohibited Unix
sockets and absent reference FLAC. The full Go race suite passes all other packages and encounters only the
previously documented prohibited Unix socket in modembridge
(`TestSupervisor_ConnectOnly_DialsExistingSocket`). Go vet also passed. No tests are
removed, disabled or weakened. See [the agent handoff](fx25-300-handoff.md) for
final commands and outstanding checks. Interactive UI/confirmation testing,
physical PTT, HF reception and on-air measurements remain unperformed.


The interop script requires Dire Wolf at
`eda1383f5fa9d8ba3cb27f99db1d2c79494404c9` with `atest` and `gen_packets` built.
It generates temporary waveforms, never opens an audio or PTT device, and leaves

the inherited 1200-baud interoperability record. Run `scripts/fx25/stress300.py`
with the same tool/reference paths for the deterministic impairment and airtime
checks; its clean, noise and clock controls are assertions, not RF benchmarks.

## Sources and limits of inference

- [FX.25 draft 0.01.06, 2006](https://eindhoven.space/wp-content/uploads/2022/12/fx-25_01_06.pdf):
  wire structure, 64-bit tag and Reed-Solomon modes. Same specification and
  provenance as [the 1200-baud implementation](fx25.md).
- [Pinned Dire Wolf source](https://github.com/wb2osz/direwolf/tree/eda1383f5fa9d8ba3cb27f99db1d2c79494404c9):
  `fx25_init.c`, `fx25_send.c`, `fx25_rec.c`, `gen_packets.c`, `gen_tone.c`.
  Its `gen_packets -B 300` uses 1600/1800 Hz AFSK. Independent interoperability
  is tested against these actual tools, not inferred from the specification.
- [Dire Wolf: AX.25 + FEC = FX.25](https://github.com/wb2osz/direwolf/blob/eda1383f5fa9d8ba3cb27f99db1d2c79494404c9/doc/AX25_plus_FEC_equals_FX25.pdf):
  redundant coding versus clean-link overhead, error-dependent application
  throughput, and asymmetric use. Its results do not establish this branch's
  300-baud HF performance. The shared-channel recommendations above are an
  inference from longer occupied time, not a measured HF collision study.

## Physical acceptance still required

Recruit a suitably equipped tester for both directions against an independent
300-baud FX.25 station; ordinary AX.25, all TX modes, repaired receptions,
long-frame/PTT duration, oversized fallback, carrier sensing, repeats, restart,
and measured busy-channel behavior need real-use verification. Record radio,
audio bandwidth, sample rate, channel conditions and exact source. Keep this
PR a tester-only draft until those results are reviewed. Android host-stub or
cross-compilation results are not Android device acceptance.
