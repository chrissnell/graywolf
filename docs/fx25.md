# Native FX.25 for 1200-baud Bell 202

Native receive runs alongside ordinary AX.25 on AFSK channels at 1200 baud,
1200 Hz mark / 2200 Hz space. `fx25_encode` (Channels → Edit → FX.25 transmit)
enables native TX. Unsupported rates, tones, modem types, KISS-only channels
and simultaneous FX.25/IL2P encoding are rejected. FX.25 at 300 baud is possible
future work, not a current capability. No 300/9600-baud, PSK/G3RUH,
experimental multi-block formats or IL2P integration is added here. For an
external KISS TNC, on-air FEC is configured in that TNC rather than by these
native-modem settings. The operator-facing scope and capability matrix are in
the [Channels handbook](handbook/channels.html#forward-error-correction).

## Repairs to the previous implementation

The base is upstream/main `bde16a1752ef96e8907aea9dc18c698e3e96a9d7`.
This work repairs the existing FX.25 codec **and** connects it to native TX/RX.
It does not replace or broadly rewrite the AFSK demodulator or IL2P codec.

| Area | Previous behavior at that base | Repair and validation |
|---|---|---|
| Correlation tags | Reserved tag 0 treated as usable; wrong tag/capacity assignments, altered values and nonstandard parity counts | Standard tags 1–11, reserved tags rejected; pinned Dire Wolf wire vectors |
| Tag bit/byte order | Encoder emitted big-endian tag bytes; receiver searched in the opposite bit direction from standard LSB-first transmission | Little-endian tag bytes, LSB-first bits, verified against real Dire Wolf |
| Protected data | Encoder copied raw frame/FCS bytes into RS data without protected HDLC delimiters or bit stuffing | Opening flag, stuffed frame/FCS, closing flag and phase-continuous flag padding |
| Shortened RS blocks | Used the shared helper's leading-zero shortening convention | FX.25-specific zero symbols restored after data/before parity; shared RS/IL2P conventions unchanged |
| Frame extraction | Stripped trailing 0x7e bytes and did not validate reconstructed HDLC/FCS | Real HDLC extraction and FCS validation; embedded/trailing literal flags preserved |
| Production TX/RX | TX ignored `fx25_encode`; FX.25 receiver had no production bit feed | Channel-controlled native TX and pre-unstuffing receive feed, restricted to Bell 202 at 1200 baud |
| Prior compatibility test | A test described as a Dire Wolf vector mainly round-tripped Graywolf's own codec | Independent pinned C wire generator, real Dire Wolf audio generator/receiver, checksummed fixtures |
| Reception visibility | Internal retry metadata was dropped before the packet log; clean HDLC delivery could hide the later FEC result | Validated FX.25 metadata retained through IPC/API/log/inspector; bounded arbitration prefers verified FEC and delivers once |

These are concrete protocol/integration fixes. They are **not evidence that
Graywolf's overall modem sensitivity or decode performance equals or exceeds
Dire Wolf**. Current evidence demonstrates specific wire/audio interoperability,
error-correction/rejection cases and bounded receiver behavior. Comparable
noisy-channel packet counts, false-positive rates, modulation quality and Pi
CPU/RSS require controlled comparative measurements. Operator RF/PTT checks
and a Pi workload baseline are recorded in [validation](fx25-validation.md). No general performance-parity or performance-gain claim is made.

## Wire format and provenance

- [FX.25 draft, 1 September 2006, document 0.01.06](http://www.stensat.org/docs/FX-25_01_06.pdf),
  [retrieved copy](https://eindhoven.space/wp-content/uploads/2022/12/fx-25_01_06.pdf),
  SHA256 `8e7d1e6f5b727b9427de4cc3a6e97eb9dbe19693762cea02211bf2eba2e2b85f`.
- [Dire Wolf reference revision](https://github.com/wb2osz/direwolf/tree/eda1383f5fa9d8ba3cb27f99db1d2c79494404c9),
  specifically `src/fx25_init.c`, `fx25_send.c`, `fx25_rec.c`,
  `fx25_encode.c`, `fx25_extract.c`, `hdlc_rec.c`, `multi_modem.c`,
  `gen_packets.c`, `gen_tone.c` and `atest.c`.
  Copyright John Langner WB2OSZ; its RS implementation credits Phil Karn KA9Q
  and Jim McGuire KB3MPL. Reference source is GPL-2.0-or-later. The adapters
  in `scripts/fx25/` invoke that source; it is not vendored into Graywolf.

Tag bytes and all codeword bytes are transmitted LSB first (tag integer in
little-endian byte order). The protected information is an opening HDLC
flag, bit-stuffed AX.25 including CRC-16/X.25 FCS (low byte first), a closing
flag, and continuing flag-pattern padding at the closing flag's bit phase.
The entire tag/data/parity transmission is NRZI encoded continuously.
RS uses GF(256), primitive polynomial 0x11d, first root 1, root step 1.
Shortened codewords omit zero symbols **after data, before parity**, not
leading zero symbols. The shared RS codec and IL2P conventions are unchanged.

| Tag | Radio data bytes | Parity bytes | Radio block bytes |
|---|---:|---:|---:|
| 1 | 239 | 16 | 255 |
| 2 | 128 | 16 | 144 |
| 3 | 64 | 16 | 80 |
| 4 | 32 | 16 | 48 |
| 5 | 223 | 32 | 255 |
| 6 | 128 | 32 | 160 |
| 7 | 64 | 32 | 96 |
| 8 | 32 | 32 | 64 |
| 9 | 191 | 64 | 255 |
| 10 | 128 | 64 | 192 |
| 11 | 64 | 64 | 128 |

Receive supports all eleven formats. Native TX follows Dire Wolf's automatic
preference order **4, 3, 6, 9, 5, 1**, selecting the first that fits the
stuffed frame. Automatic is recommended for everyday use. Choose a fixed 16/32/64-parity
mode for specific use cases or controlled testing. The channel editor places
this mode selector next to the FX.25 transmit toggle. Fixed modes select the
shortest standard block with the requested parity count. They do not switch
parity families: if no block fits, production TX uses ordinary AX.25 and
explicitly labels the packet **AX.25 fallback**, as does Automatic.
Tags 0 and 12–15 are reserved/undefined and are never accepted.

## Limits and delivery behavior

The protected frame including flags, stuffing and FCS must fit 239 bytes.
AX.25 input before FCS must be 15–235 bytes, including addresses, control,
PID and information; the maximum information payload is therefore smaller
(e.g. at most 219 bytes with two addresses, UI control and PID). Bit stuffing
can reduce the 235-byte limit; 195 AX.25 bytes always fit regardless of bit
patterns. These are FX.25 limits, not limits on ordinary AX.25 fallback.
The Rust production builder checks the actual stuffed length while creating
audio. If the selected mode cannot fit the frame, it builds ordinary AX.25
without truncation and reports `fallback_reason: "frame_too_large"`. This
applies to Automatic and fixed parity modes, following Dire Wolf. Invalid
configuration or a malformed frame is still an error; fallback never hides
an unsupported FX.25 rate or modulation.

The full tag, protected data and parity are included in the audio buffer
passed to the existing TX queue/drain/PTT worker. TX delay/tail remain flag
preamble/postamble durations. No extra PTT driver or polarity behavior changes.

Each supported slicer feeds FX.25 from NRZI-decoded data before HDLC unstuffing.
RS decoding is followed by strict ordinary HDLC/FCS validation, without bit
retry repair. A receiver retains at most one 255-byte block; collection ends
within 2040 bits and tag search continues to recover after truncated blocks.
Tag matching does at most eleven popcounts per bit, accepting up to eight
corrupted tag bits. RS codecs are initialized once and reused.

Dedup compares payload and the embedded closing-flag sample position within
three symbols, including across slicers and the ensemble. That position is
backdated when FEC finishes. The history is retained for three seconds to
cover parity latency, with a 128-event per-demod cap; the matching window
itself is not three seconds. Later repeats remain distinct. Ensemble history
expires too. A valid HDLC candidate inside a detected FX.25 block is held
until the FEC result is available, so clean frames retain FX.25 identification.
This also applies across ensemble profiles. If FEC fails, the valid HDLC
candidate remains a fallback without any claim of successful FEC decoding.
This follows the pinned Dire Wolf receive design: `hdlc_rec.c` feeds both
paths, `multi_modem.c` waits while `fx25_rec_busy` and prefers a successful
FX.25 candidate, and an ordinary FCS-valid candidate survives FEC failure.
The hold applies only while a block is detected; its absolute timeout is one
maximum codeword plus 25% clock tolerance (2.125 seconds at 1200 baud), and
pending queues have a 128-frame cap. Ordinary AX.25 without an active FX.25
candidate remains immediate. Reconfiguration clears pending state.

The packet log shows **FX.25**, **FEC decoded · N symbols repaired**, tag and
parity. Type, encoding and origin badges wrap within their column, including
Digipeater and AX.25 fallback labels; badges are not truncated to make them fit.
A clean codeword has zero repaired symbols. The inspector adds the
RS block parameters and FCS validation result. These labels require both RS
and embedded HDLC/FCS success; a tag match or TX configuration alone is not
enough. Corrections count codeword bytes (including parity), excluding tag
bit errors. Native ordinary HDLC frames show AX.25; KISS sources carry no
inferred native FEC metadata. Signal levels, channel/slice and quality remain
available. FEC-only speed error is unavailable (zero).

## Channel and packet API for external applications

`GET /api/channels` and `GET /api/channels/{id}` expose:

```json
{"fx25_encode": true, "fx25_mode": "auto"}
```

`fx25_encode` controls TX only and defaults to false, matching Dire Wolf's
normal APRS `FX25TX` default. `fx25_mode` is `"auto"` (recommended/default),
`"16"`, `"32"` or `"64"`. It is retained while TX is disabled. There is no
public numeric `0 = auto` setting to confuse with Dire Wolf's `FX25TX 0 = off`.
Channel POST/PUT accepts these same fields. They describe saved configuration,
not proof of successful transmission or a successfully running audio device.
RX recognizes all standard 16/32/64-parity formats automatically on supported
native channels regardless of the TX toggle/mode.

`GET /api/packets` and the existing packet stream carry a non-null `fx25`
object **only for verified native FX.25 reception**:

```json
{"fx25":{"tag":6,"data_bytes":128,"parity_bytes":32,"corrected_symbols":0}}
```

Zero corrected symbols means a clean, verified codeword. An absent `fx25`
object means no verified FX.25 decode was reported; it does not prove that no
FX.25 transmission was present or that an external KISS TNC used no FEC.
PacketRover can consume these API fields; this change does not modify it.

Mode capacity (including flags, stuffing and FCS) is 239 bytes with 16 parity,
223 with 32 parity, and 191 with 64 parity. A fixed mode can therefore use
ordinary AX.25 fallback for a frame that Automatic would fit using another
standard parity family. There is one authoritative encoder selection in Rust,
not a second Go implementation predicting the result.

Automatic matches the pinned Dire Wolf `FX25TX 1` preference, based only on
protected size; it does not measure link quality:

| Required protected bytes | Tag | Parity bytes |
|---|---|---:|
| Up to 32 | 0x04 | 16 |
| 33–64 | 0x03 | 16 |
| 65–128 | 0x06 | 32 |
| 129–191 | 0x09 | 64 |
| 192–223 | 0x05 | 32 |
| 224–239 | 0x01 | 16 |
| Over 239 | Ordinary AX.25 fallback | None |

These sizes include flags, stuffing and FCS, not just an APRS comment. Tag,
padding and parity increase airtime according to the selected block; there
is no universal airtime multiplier.

Native TX rows are enriched with the actual encoder result through
`GET /api/packets`, for example:

```json
{"frame_id":42,"tx_encoding":{"encoding":"fx25","tag":9,"data_bytes":191,"parity_bytes":64,"fx25_requested":true}}
```

For an oversized frame:

```json
{"frame_id":43,"tx_encoding":{"encoding":"ax25","fx25_requested":true,"fallback_reason":"frame_too_large"}}
```

Ordinary native TX with FX.25 disabled reports `encoding: "ax25"` and
`fx25_requested: false`. KISS sources are not assigned inferred encoding.
The dashboard/inspector shows the TX tag/parity or explicit AX.25 fallback.
These reports mean encoding and local queue acceptance, not PTT completion
or successful RF reception. TX metadata may arrive after the initial packet
stream event. It enriches the existing row without broadcasting another
packet event; integrations should refresh recent `GET /api/packets` rows.
A timestamp-only `since` query does not resend an older enriched row.
`frame_id` is process-local and resets on app restart.

## Carrier sensing and queue status

Beacon Now queues a request; the UI says **queued**. The legacy beacon-send
API response `status: "sent"` remains queue acceptance for compatibility.
Half-duplex carrier sensing, persistence and configured rate limits can defer
transmission. Repeated clicks can queue multiple frames.

A separate supporting fix reconciles cached DCD with authoritative modem
status (`StatusUpdate.dcd_state_valid`). Audio reconfiguration can reset the
receiver without a fresh carrier edge; previously the Go governor could keep
an old busy state until another RX event, delaying queued frames. Valid quiet
status now clears that stale state. Invalid/placeholder status is ignored;
genuine busy carrier still inhibits TX. There is no forced-transmit timeout
and no requirement to decode a packet before transmitting. The operator's
final check reported near-zero delay after this fix.

A literal output-only native channel still requires an input-device binding
in current backend selection. This existing wiring limit is separate from
DCD and is not resolved by this FX.25 change.

## Reproduce independent acceptance

Requires Rust/Cargo, protoc, ALSA development headers, C compiler, CMake,
Python 3 and Git. All commands below are offline audio/file operations;
they never open an audio device or key PTT.

```sh
git clone https://github.com/wb2osz/direwolf.git /tmp/direwolf-fx25-reference
git -C /tmp/direwolf-fx25-reference checkout --detach eda1383f5fa9d8ba3cb27f99db1d2c79494404c9
cmake -S /tmp/direwolf-fx25-reference -B /tmp/direwolf-fx25-reference/build
cmake --build /tmp/direwolf-fx25-reference/build --target gen_packets atest -j4
cargo build --example fx25_audio
python3 scripts/fx25/interop.py /tmp/direwolf-fx25-reference
(cd graywolf-modem/testdata/fx25 && sha256sum -c SHA256SUMS)
cargo test --release --lib fx25
cargo test --release --lib il2p
```

`--generate` on the Python command regenerates fixtures. Its checks cover 33
byte-exact wire vectors, 33 Graywolf-to-real-Dire-Wolf audio decodes (including
byte-for-byte output and exactly one delivery), four additional production
TX-mode cases (auto/16/32/64), four oversized production fallback cases,
33 real-Dire-Wolf-to-Graywolf
audio decodes and eleven symbol-damaged recordings requiring FEC recovery.
Every standard tag is exercised. Wire vectors include exact capacity
boundaries/maximum frames, embedded flags, FF, zero and flag-ending payloads.
Generated text audio includes short, intermediate and near-maximum frames.
Checked-in audio additionally runs through production channel creation and
single/triple decoder dispatch in `modem::fx25_acceptance` tests.

Unit tests cover correction at parity/2 symbols, deterministic uncorrectable
blocks, FCS rejection despite valid RS, reserved/invalid tags, partial blocks,
noise, reset, back-to-back frames, mixed ordinary traffic, repeated payloads,
configuration scope, exact duration including parity and excessive lengths.
These demonstrate protocol interoperability, not RF/noise performance gains.
The identical-ensemble comparison additionally demonstrates 11/11 damaged
fixture recoveries with FX.25 versus 0/11 with ordinary HDLC/FCS alone; both
paths recover the clean 33/33 control. See `fx25-validation.md` for exact
conditions and the reproducible test command.
