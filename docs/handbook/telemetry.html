Station Activity Telemetry

Native station-wide ten-minute T# reporting

Open Settings → Telemetry. Reporting is off by default. One reporter measures the entire Graywolf instance across all channels. The RF delivery channel controls where a report is transmitted, not which activity is counted. Per-channel reporting and digital status telemetry are possible future work.

The next sequence and definition refresh timestamps are stored in the SQLite configuration database selected by Graywolf's -config flag. The next sequence is saved before submitting each report. Normal restart continues that sequence, wrapping after 999. Restoring an older database snapshot also restores its older sequence; appliances must keep runtime state durable separately from configuration rollback if needed. Samples and recent submission history are held only in RAM.

Measurements and Scope

SlotLabelMeaning over the preceding ten minutes
1RF RxNative received frames plus decoded KISS-TNC ingress; KISS application/modem-mode input and APRS-IS reception are excluded.
2DigiBackend-forwarded digipeater frames when that accounting is available; otherwise legacy processed submissions, including TX-stage duplicates.
3RF TxRF backend dispatches across all channels, including telemetry. This is not an airtime or confirmed-radiation counter.
4RF → ISThe existing iGate upload counter, including simulated uploads in simulation mode.
5IS → RFRequests accepted without a governor error, including suppressed duplicates; not confirmed RF transmissions.

A packet received on two channels counts as two reception events. Disconnected inputs contribute no receptions; reports do not prove continuous receiver availability. Forwarded means at least one backend accepted a frame, counted once regardless of backend fanout. No counter confirms remote reception.

Identity and Delivery

Leave Telemetry callsign/SSID blank to inherit and follow the station identity. An explicit override remains fixed; use only an identity you are authorized to transmit. Data and self-addressed definitions use the same identity on both delivery routes. Avoid another telemetry publisher using that same identity with different measurements or definitions.

APRS-IS only is the default and recommended for Internet-connected stations. It avoids additional RF airtime and waits during an Internet outage. Existing saved delivery choices are preserved. Selecting RF-only or APRS-IS preferred with RF fallback requires an RF delivery channel before settings can be saved, even while reporting is disabled. Enabled RF delivery also requires a TX-capable channel.

  • APRS-IS preferred; RF when disconnected: use the connected APRS-IS session, otherwise the selected ready RF channel.
  • APRS-IS only: wait when disconnected; never fall back to RF.
  • RF only: use the selected APRS/TX-capable channel. The optional RF digipeater path is separate from position beacons; blank means direct.

Readiness uses enabled native channels with running modem status, or connected KISS-TNC interfaces (a listening TCP server alone is insufficient). A first report does not require a received packet, PTT, or Internet access: a quiet receive-only input can establish the baseline. Actual RF delivery additionally requires a usable output and configured PTT, or a connected TX-enabled KISS TNC. Simulation mode is not treated as an active APRS-IS reporting route.

Startup, Timing and Failures

Reporting period and measurement window are both ten minutes, observed at ten-second sampling resolution (scheduler jitter can slightly lengthen the measured window). Collection starts only when counters and at least one enabled RF input are ready. The first report requires a full baseline. Later interface disconnects do not reset valid cumulative observations; unavailable/decreasing counters, a sampling gap longer than 90 seconds, changed settings or reporting identity, and a change between forwarded/legacy Digi accounting restart collection.

After the first data submission, due definitions follow in this order: PARM, UNIT, EQNS, with 30 seconds between packets and before the first definition. There is no separate startup-delay setting. The same rule applies when first reporting on a different route. Receivers may initially show generic labels until they receive definitions.

Definitions refresh every two hours on APRS-IS and six hours on RF by default; advanced settings accept one hour through seven days. Sequence numbers wrap after 999 and are reserved before sending. Sequence and completed-definition times persist; samples remain in bounded RAM and always warm up after restart. Missed reports are skipped instead of replayed as a burst. An uncertain send is not retried immediately on another route.

RF packets use the ordinary governor, channel rate limits, carrier sensing, backend and modem encoding. Telemetry queued in the governor expires after two minutes and is canceled when its reporter is reset. Backend buffering after acceptance is separate; local submission is not TX completion. The manual Send report now action requires a full valid baseline and allows at most one manual report per 30 seconds. Merely viewing or saving the page does not send a packet immediately.

Counts Above 255

By default, transmitted counts saturate at 255 and the page warns when a value is clipped. Local UI/API counts remain exact. Advanced Allow counts above 255 transmits exact larger integers without scaling. This extended T# form is supported by aprs.fi, but strict older decoders may reject it. There is no multiplier or five-minute mode. Units remain pkt/10m and identity equations 0,1,0 apply to all five values.

No active digital flags are implemented. The unused digital field is 00000000 for compatibility; no BITS definition is generated.

API and Testing

Authenticated GET/PUT /api/telemetry/config reads/replaces saved configuration. GET /api/telemetry/status exposes warmup/readiness, effective identity, Digi provenance, exact/encoded counts, clipping, preview, route, last submission and error. A recent-submissions table retains at most ten data reports in RAM, including identity, route, exact/encoded values and payload; it clears on restart and is not proof of reception. POST /api/telemetry/report requests a real manual report; 202 means local submission, not RF reception. See the API reference.

Before operator testing, review delivery, identity, RF path and schedules. Inspect the first ten-minute report followed by its definitions at a separate receiver, confirm no startup transmission, test disable/restart and disconnected transport behavior, and check the report on aprs.fi if using extended values. Automated tests use virtual clocks and fake transports; no unattended RF test is included.
